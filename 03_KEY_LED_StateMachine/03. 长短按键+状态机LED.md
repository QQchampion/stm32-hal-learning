# 03. 长短按键 + 状态机控制 LED

## 1. 实验目标

- 在上一节“KEY 控制 LED”的基础上，识别按键的短按和长按；
- 使用 `HAL_GetTick()` 计算按键持续时间；
- 理解状态机为什么需要保存“上一次状态”；
- 将 GPIO 初始化、按键识别、LED 控制和业务逻辑拆分到不同模块；
- 使用枚举表示按键事件和 LED 状态，提高代码可读性；
- 理解当前程序的事件产生时机、优点和局限。

---

## 2. 硬件信息

本工程使用 KEY1 控制绿色 LED。CubeMX 中还配置了 KEY2、蓝色 LED 和红色 LED，但本次长短按逻辑暂未使用它们。

| 器件 | GPIO 引脚 | 配置模式 | 有效电平 | 本实验用途 |
| --- | --- | --- | --- | --- |
| KEY1 | `PA0` | 输入、无上下拉 | 高电平按下 | 识别短按和长按 |
| KEY2 | `PC13` | 输入、无上下拉 | 高电平按下 | 已配置，暂未使用 |
| LED_G | `PB0` | 推挽输出 | 低电平点亮 | 短按点亮，长按熄灭 |
| LED_B | `PB1` | 推挽输出 | 低电平点亮 | 已配置，暂未使用 |
| LED_R | `PB5` | 推挽输出 | 低电平点亮 | 已配置，暂未使用 |

对应宏定义位于 `Core/Inc/main.h`：

```c
#define KEY_2_Pin GPIO_PIN_13
#define KEY_2_GPIO_Port GPIOC
#define KEY_1_Pin GPIO_PIN_0
#define KEY_1_GPIO_Port GPIOA
#define LED_G_Pin GPIO_PIN_0
#define LED_G_GPIO_Port GPIOB
#define LED_B_Pin GPIO_PIN_1
#define LED_B_GPIO_Port GPIOB
#define LED_R_Pin GPIO_PIN_5
#define LED_R_GPIO_Port GPIOB
```

本开发板的 LED 为低电平点亮：

```text
GPIO_PIN_RESET（低电平）→ LED 点亮
GPIO_PIN_SET（高电平）  → LED 熄灭
```

`MX_GPIO_Init()` 将 `PB0`、`PB1`、`PB5` 的初始电平设为高电平，因此上电后 LED 默认熄灭。

> `GPIO_NOPULL` 表示不启用 STM32 内部上拉或下拉电阻，输入电平由开发板外部电路保证。若换用其他开发板，必须重新确认原理图和按键有效电平。

## 3. 从上一节到本节的改进

上一节使用“检测按下 → 延时消抖 → 等待松手”的方式，一次按压只返回一次事件：

```c
while (HAL_GPIO_ReadPin(GPIOx, GPIO_Pin) == GPIO_PIN_SET)
{
}
```

这种方法适合简单实验，但等待松手期间 CPU 一直被占用，无法继续处理其他任务，也不方便判断按住了多长时间。

本节不再使用 `while` 等待松手，而是在主循环中持续调用 `Key_Scan()`。函数利用 `static` 变量记住按键是否已经按下、按下时间以及是否已经产生长按事件。每次调用只检查当前状态，然后立即返回一个事件：

```text
KEY_EVENT_NONE         当前没有新事件
KEY_EVENT_SHORT_PRESS  产生一次短按事件
KEY_EVENT_LONG_PRESS   产生一次长按事件
```

这使程序能够在等待按键变化的同时继续执行主循环中的其他任务。当前实现仅在首次确认按下和确认释放时调用 `HAL_Delay(20)`，因此它是“主体非阻塞、消抖处短暂阻塞”的实现。

## 4. 工程模块划分

```text
gpio.c / gpio.h：CubeMX 生成，负责 GPIO 时钟、输入输出模式和初始电平
key.c  / key.h ：负责按键消抖、计时以及长按/短按事件识别
led.c  / led.h ：负责把 LED 逻辑状态转换成实际 GPIO 电平
main.c          ：读取按键事件，并决定不同事件对应的 LED 行为
```

这种划分的核心是“每个模块只负责一类事情”：

- GPIO 层只关心硬件如何初始化；
- KEY 层只关心用户做了哪一种按键动作；
- LED 层只关心灯应该处于什么状态；
- `main.c` 只保留最上层的业务规则。

`gpio.c` 通常由 CubeMX 自动生成。自定义按键逻辑放入 `key.c`、LED 控制放入 `led.c`，可以降低重新生成代码时被覆盖的风险。

## 5. 用枚举描述状态和事件

### 5.1 按键事件

`Core/Inc/key.h` 中定义：

```c
typedef enum
{
    KEY_EVENT_NONE = 0,
    KEY_EVENT_SHORT_PRESS,
    KEY_EVENT_LONG_PRESS
} KEY_EVENT;

KEY_EVENT Key_Scan(void);
```

相比直接返回 `0`、`1`、`2`，`KEY_EVENT_SHORT_PRESS` 这样的名字能够直接表达含义，减少“魔法数字”。这里返回的是“事件”，不是按键当前的高低电平：事件只在特定时刻出现一次，其余扫描都会返回 `KEY_EVENT_NONE`。

### 5.2 LED 状态

`Core/Inc/led.h` 中定义：

```c
typedef enum
{
    LED_ON,
    LED_OFF
} LED_STATE;

void LED_SetState(LED_STATE state);
```

上层代码只需要表达 `LED_ON` 或 `LED_OFF`，不需要反复记忆“低电平才是点亮”。逻辑状态与硬件电平之间的转换统一放在 LED 模块中。

## 6. LED 状态控制

`Core/Src/led.c` 的核心逻辑为：

```c
void LED_SetState(LED_STATE state)
{
    switch (state)
    {
        case LED_OFF:
            HAL_GPIO_WritePin(LED_G_GPIO_Port, LED_G_Pin, GPIO_PIN_SET);
            break;

        case LED_ON:
            HAL_GPIO_WritePin(LED_G_GPIO_Port, LED_G_Pin, GPIO_PIN_RESET);
            break;
    }
}
```

| 逻辑状态 | GPIO 输出 | LED 实际状态 |
| --- | --- | --- |
| `LED_ON` | `GPIO_PIN_RESET` | 点亮 |
| `LED_OFF` | `GPIO_PIN_SET` | 熄灭 |

当前工程源码中直接写了 `GPIOB` 和 `GPIO_PIN_0`，功能上是正确的；使用 CubeMX 生成的 `LED_G_GPIO_Port` 和 `LED_G_Pin` 宏，可让代码含义更明确，也便于以后修改引脚。

## 7. 长按与短按识别

### 7.1 时间参数

```c
#define KEY_LONG_PRESS_TIME  1000U
#define KEY_DEBOUNCE_TIME      20U
```

- `KEY_DEBOUNCE_TIME`：按下或释放后等待 20 ms，再次采样以过滤机械抖动；
- `KEY_LONG_PRESS_TIME`：持续按住达到 1000 ms，判定为长按。

这两个值可以根据按键硬件和实际手感调整。`100 ms` 通常更接近普通按压或较长的消抖时间，不适合作为明显的长按阈值。

### 7.2 为什么使用 `static` 变量

```c
static uint8_t key_pressed = 0;
static uint8_t long_pressed = 0;
static uint32_t press_time = 0;
```

局部变量通常会在函数返回后失去原来的值；`static` 局部变量只初始化一次，并能在多次调用之间保存数据，因此可以充当状态机的“记忆”。

| 变量 | 含义 |
| --- | --- |
| `key_pressed` | 是否已经确认本次按下有效 |
| `long_pressed` | 本轮按压是否已经产生过长按事件 |
| `press_time` | 确认按下时的系统毫秒时间 |

### 7.3 `HAL_GetTick()` 的作用

`HAL_GetTick()` 返回系统启动后累计的毫秒数。确认按键按下时记录起始时间：

```c
press_time = HAL_GetTick();
```

之后用当前时间减去起始时间得到持续时间：

```c
HAL_GetTick() - press_time >= KEY_LONG_PRESS_TIME
```

这里采用无符号整数相减，即使系统 Tick 在长时间运行后溢出回绕，这种写法在时间间隔小于计数范围时仍能正常判断，比直接比较绝对时间更稳妥。

### 7.4 当前 `Key_Scan()` 的完整逻辑

```c
KEY_EVENT Key_Scan(void)
{
    static uint8_t key_pressed = 0;
    static uint8_t long_pressed = 0;
    static uint32_t press_time = 0;
    GPIO_PinState key_level;

    key_level = HAL_GPIO_ReadPin(KEY_1_GPIO_Port, KEY_1_Pin);

    if (key_level == GPIO_PIN_SET)
    {
        if (key_pressed == 0)
        {
            HAL_Delay(KEY_DEBOUNCE_TIME);

            if (HAL_GPIO_ReadPin(KEY_1_GPIO_Port, KEY_1_Pin) == GPIO_PIN_SET)
            {
                key_pressed = 1;
                long_pressed = 0;
                press_time = HAL_GetTick();
            }
        }

        if ((key_pressed == 1) &&
            (long_pressed == 0) &&
            (HAL_GetTick() - press_time >= KEY_LONG_PRESS_TIME))
        {
            long_pressed = 1;
            return KEY_EVENT_LONG_PRESS;
        }
    }
    else
    {
        if (key_pressed == 1)
        {
            HAL_Delay(KEY_DEBOUNCE_TIME);

            if (HAL_GPIO_ReadPin(KEY_1_GPIO_Port, KEY_1_Pin) == GPIO_PIN_RESET)
            {
                key_pressed = 0;

                if (long_pressed == 0)
                {
                    return KEY_EVENT_SHORT_PRESS;
                }

                long_pressed = 0;
            }
        }
    }

    return KEY_EVENT_NONE;
}
```

工程当前使用的是 `GPIOA`、`GPIO_PIN_0`，上面改用 `KEY_1_GPIO_Port`、`KEY_1_Pin` 展示，二者对应同一引脚。

## 8. 状态机执行过程

虽然当前代码没有显式定义 `IDLE`、`PRESSED` 等状态枚举，但 `key_pressed` 和 `long_pressed` 的组合已经构成了一个简化状态机。

```text
空闲状态：key_pressed = 0
    │
    │ 检测到高电平，延时 20 ms 后仍为高电平
    ▼
已按下、尚未长按：key_pressed = 1，long_pressed = 0
    │                         │
    │ 1 秒内稳定释放          │ 持续时间达到 1000 ms
    ▼                         ▼
产生 SHORT 事件          产生一次 LONG 事件
回到空闲状态             long_pressed = 1
                              │
                              │ 稳定释放
                              ▼
                         回到空闲状态，不再产生短按
```

### 8.1 短按过程

1. KEY1 由低电平变为高电平；
2. 延时 20 ms 后再次读取，仍为高电平，确认按下；
3. 设置 `key_pressed = 1`，记录 `press_time`；
4. 在 1000 ms 以内松开；
5. 延时 20 ms 后确认仍为低电平；
6. 因为 `long_pressed == 0`，返回一次 `KEY_EVENT_SHORT_PRESS`。

短按事件在“确认释放”时产生，因为只有到释放时，程序才能确定本轮按压没有达到长按阈值。

### 8.2 长按过程

1. 按下并通过 20 ms 消抖；
2. 持续按住，主循环不断调用 `Key_Scan()`；
3. 当持续时间达到 1000 ms 时，返回一次 `KEY_EVENT_LONG_PRESS`；
4. 同时设置 `long_pressed = 1`，防止继续按住时重复产生长按事件；
5. 松开后只复位内部状态，不再产生短按事件。

长按事件在“达到阈值”时产生，不必等到松开。因此灯会在按住约 1 秒时立即执行长按功能。

## 9. `main.c` 中的事件处理

```c
while (1)
{
    KEY_EVENT key_event;
    key_event = Key_Scan();

    switch (key_event)
    {
        case KEY_EVENT_SHORT_PRESS:
            LED_SetState(LED_ON);
            break;

        case KEY_EVENT_LONG_PRESS:
            LED_SetState(LED_OFF);
            break;

        case KEY_EVENT_NONE:
        default:
            break;
    }
}
```

| 按键事件 | LED 操作 | 实际现象 |
| --- | --- | --- |
| 短按 KEY1 | `LED_SetState(LED_ON)` | 绿色 LED 点亮 |
| 长按 KEY1 | `LED_SetState(LED_OFF)` | 绿色 LED 熄灭 |
| 无事件 | 不操作 | 保持原状态 |

与在 `main.c` 中直接读写 GPIO 相比，这种写法更接近自然语言：扫描按键、取得事件、根据事件设置灯的状态。

## 11. 本次问题与关键理解

### 11.1 为什么简单扫描两次不能可靠区分长短按

曾考虑第一次扫描到按下，延时一段时间后再次扫描；第二次仍按下就认为是长按，否则认为是短按。这种方法存在几个问题：

- 如果扫描函数内部等待松手，第二次调用时按键已经释放；
- 固定延时会阻塞 CPU，延时越长，其他任务越长时间得不到执行；
- 只取两个时刻的电平，没有完整表示“按下、保持、释放”的过程；
- `100 ms` 的阈值通常过短，容易把普通按压误认为长按。

正确思路是记录确认按下的时间，并在后续循环中持续计算按住时长。

### 11.2 为什么长按后不会再触发短按

达到长按阈值时设置 `long_pressed = 1`。释放时只有 `long_pressed == 0` 才返回短按事件，因此一次按压只会被归类为短按或长按，不会同时产生两种事件。

### 11.3 为什么长按只触发一次

第一次达到阈值后，`long_pressed` 被设为 `1`。继续按住时，长按判断要求 `long_pressed == 0`，所以不会重复返回长按事件；释放后才将它复位，为下一轮按压做准备。

### 11.4 当前编译警告

当前工程能够链接，构建记录为 `0 Error(s), 1 Warning(s)`。警告来自 `main.c`：

```text
variable "led_state" was declared but never referenced
```

原因是程序仍保留了：

```c
LED_STATE led_state = LED_OFF;
```

但现在直接调用 `LED_SetState(LED_ON)` 和 `LED_SetState(LED_OFF)`，没有使用 `led_state`。如果不需要保存 LED 状态，可以删除这个变量；如果要实现“短按翻转”，则可以保留并实际更新它。

### 11.5 源码注释出现乱码

当前部分 `.c/.h` 文件的中文注释出现乱码，通常是 Keil、编辑器与文件使用的字符编码不一致。可以统一保存为 UTF-8，并确认编辑器按 UTF-8 打开；如果旧版 Keil 对 UTF-8 支持不理想，也可以使用英文注释。

## 12. 当前实现的优点与局限

### 优点

- 不再使用死循环等待松手，主循环可以持续运行；
- 长按通过真实持续时间判断，而不是简单延时后猜测；
- 一次长按只触发一次，长按释放后不会误触发短按；
- 按键、LED 和业务逻辑已经模块化；
- 枚举让事件和状态含义更清晰。

### 局限

- 消抖阶段仍使用 `HAL_Delay(20)`，会短暂阻塞；
- 当前 `Key_Scan()` 把 KEY1 引脚写死，只能处理一个按键；
- 状态由两个布尔变量隐式表达，功能变复杂后不如显式状态枚举直观；
- LED 模块目前只控制绿色 LED；
- 按键扫描依赖主循环被频繁调用，主循环中不能加入很长的阻塞延时；
- 阈值附近的按压会根据扫描时机被归入长按或短按，实际项目可加入更严格的策略。

---

## 13. 后续可以继续改进

1. 用 `IDLE`、`DEBOUNCE_PRESS`、`PRESSED`、`LONG_REPORTED`、`DEBOUNCE_RELEASE` 等枚举建立完全非阻塞状态机；
2. 让 `Key_Scan()` 接收端口和引脚参数，或为每个按键保存独立状态，以支持 KEY1、KEY2；
3. 为 LED 增加编号参数，使同一接口可以控制绿、蓝、红三盏灯；
4. 增加 `LED_ToggleState()`，实现短按切换亮灭；
5. 增加长按连续触发、双击等更复杂的按键事件；
6. 清理未使用的 `led_state` 变量，使工程达到零警告；
7. 将源码中的硬编码引脚替换为 CubeMX 生成的标签宏。

## 14. 实验现象

- 上电后绿色 LED 默认熄灭；
- 短按 KEY1 并释放，绿色 LED 点亮；
- 按住 KEY1 约 1 秒，绿色 LED 熄灭；
- KEY1 持续按住超过 1 秒时，长按事件只产生一次；
- 长按后松手不会再触发短按事件；
- KEY2、蓝色 LED 和红色 LED 虽然已经配置，本实验程序暂未使用。

## 15. 实验总结

本实验最重要的进步不是多控制了一盏灯，而是从“读取当前电平”过渡到了“识别一段时间内发生的事件”。

```text
读取 GPIO 电平
      ↓
消抖并记住按下状态
      ↓
用 HAL_GetTick() 计算持续时间
      ↓
输出短按或长按事件
      ↓
main.c 根据事件决定 LED 行为
```

需要掌握的核心结论：

- 状态机必须保存历史状态，`static` 变量为本实验提供了这种“记忆”；
- 短按需要等到释放后才能确认，长按可在达到阈值时立即确认；
- `long_pressed` 既防止长按重复触发，也避免长按释放时再产生短按；
- `HAL_GetTick()` 适合进行非阻塞式时间判断；
- 模块化的目的不是让 `main.c` 没有代码，而是让它只保留清晰的上层控制关系；
- 逻辑状态与硬件有效电平应由驱动模块统一转换。

> 核心过程：配置 GPIO → 确认按下并消抖 → 记录按下时间 → 持续扫描 → 判断短按/长按 → 返回事件 → 根据事件设置 LED 状态。
